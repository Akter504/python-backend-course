# lab1 — приём и анализ лабораторных работ

## Установка и запуск

В PowerShell из папки `lab1`:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.lock
.\.venv\Scripts\python.exe -m pip install --no-build-isolation -e .
.\.venv\Scripts\python.exe -m lab1 demo
```

Активация окружения не требуется. В Linux/macOS используйте `.venv/bin/python`.
Для установки только приложения: `python -m pip install .`.
После установки доступны `python -m lab1` и команда `lab1`.

`demo` работает из любого каталога, в том числе после установки wheel. Он показывает
12 принятых сдач, 12 дубликатов, конфликт без перезаписи и 36 результатов трёх
анализаторов. В хранилище остаётся 12 сдач. Идентификаторы результатов и время
создаются заново; наблюдения и хеши воспроизводимы.

## Команды

```powershell
.\.venv\Scripts\python.exe -m lab1 import data/submissions.jsonl
.\.venv\Scripts\python.exe -m lab1 import data/invalid_submissions.jsonl
.\.venv\Scripts\python.exe -m lab1 import data/conflict_submissions.jsonl
.\.venv\Scripts\python.exe -m lab1 analyze data/submissions.jsonl --assignments data/assignments.json --config config/app.json
```

Обычный `analyze` использует два анализатора и выдаёт 24 результата для 12 сдач.
Каждый запуск создаёт новое хранилище в памяти. Повторный импорт и конфликт между
вызовами демонстрируются в одном приложении командой `demo`; их также можно
проверить записями внутри одного JSONL-файла.

Код завершения: `0` — успех, `1` — ошибки отдельных записей или анализа,
`2` — ошибка конфигурации либо недоступный файл. Результаты и частичные ошибки
выводятся в stdout, ошибка запуска — в stderr. Вывод JSON использует UTF-8.
Ошибки записей содержат `line`, `code`, `field`, `message`. Импорт ожидает UTF-8
без BOM; пустая строка, повреждённый JSON и неверная кодировка строки считаются
ошибками, после которых обработка следующих строк продолжается.

## Устройство

```text
src/lab1/
  domain/         модели, ошибки, Protocol, хеши и контракт результата
  services/       приём, импорт, реестр и запуск анализаторов
  adapters/       валидация, источники, хранилище и анализаторы
  application.py  сборка зависимостей
  config.py       конфигурация и загрузка заданий
  cli.py          команды import, analyze и demo
tests/            модульные, контрактные и интеграционные проверки
data/             учебные сдачи и сценарии ошибок
config/app.json   список анализаторов и версия конфигурации
```

Сырые данные поступают через `accept_payload`, `accept_json` или `parse_submission`.
Pydantic DTO проверяет обязательные поля, типы, часовой пояс, непустые текст/код
и AI-декларацию. Неявные преобразования и неизвестные поля запрещены.
При `used=true` нужны инструмент и цель; `verified_by_student` сохраняется как
заявлено. Первая ошибка возвращается как `SubmissionError(code, field, message)`.
Аннотации и прямое создание dataclass сами по себе входные данные не проверяют.
Сервис приёма работает с проверенным неизменяемым доменным объектом.

SHA-256 вычисляется по всем полям сдачи через JSON с отсортированными ключами,
без лишних разделителей, в UTF-8. Текст, код и строка времени не нормализуются.
При одинаковом идентификаторе и содержимом возвращается сохранённая сдача;
при другом содержимом возникает конфликт, сохранённая версия не заменяется.

Два источника реализуют общий контракт: JSONL-файл и набор объектов в памяти.
Файловый источник управляет открытым файлом через контекстный менеджер;
ресурс закрывается при завершении, досрочном выходе и исключении.

`LengthAnalyzer` считает непустые строки текста и кода. `TemplateAnalyzer` ищет
точные последовательности строк разрешённого шаблона задания, включая
перекрывающиеся совпадения. Пробелы не нормализуются, пустой шаблон совпадений
не даёт. Оба возвращают пояснения, `score=null` и evidence с номерами исходных строк.

Сервис анализа проверяет идентификаторы, версии, хеши, score, пояснения и границы
evidence. Ошибка анализатора становится `AnalysisFailure`; исходная сдача
сохраняется. `AnalysisContext` содержит задание, версию конфигурации и заменяемый
`SubmissionReader.get` для доступа к принятым сдачам. Хеш конфигурации включает
требования задания, шаблон и версию; объект доступа к данным в него не входит.

## Подключение третьего анализатора

`Analyzer` — структурный Protocol с `analyze`, `analyzer_id`, `analyzer_version`.
`DeclarationAnalyzer` проверяет непустую AI-декларацию при `used=true` и подключается
через реестр фабрик без изменения центрального сервиса. В `demo` он уже включён.

```python
from lab1 import build_application
from lab1.adapters.analyzers import DeclarationAnalyzer
from lab1.config import parse_config

config = parse_config({"analyzers": [{"name": "declaration"}]})
app = build_application(config, extra_factories={"declaration": DeclarationAnalyzer})
```

При сборке приложения проверяются имена, фабрики и параметры анализаторов.
Пустой список, дубликат, неизвестное имя, ошибка фабрики и неподдерживаемые
параметры приводят к `ConfigurationError`. В этой лабораторной `options` — только `{}`.

## Проверки и сборка пакета

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\python.exe -m build
```

Тесты проверяют валидный импорт, повреждённый JSON, неверные типы, дубликат,
конфликт, ошибку анализатора, освобождение файла, диапазоны evidence и неизменность
входных и сохранённых объектов. Дополнительно проверяются оба источника,
заменяемость анализаторов, конфигурация и запуск установленного пакета.

## Данные

`submissions.jsonl` содержит 12 объектов из `PUBLIC_SUBMISSIONS` ноутбука
«Лекция.ipynb», извлечённых без выполнения ячеек. `assignments.json` составлен
по примеру задания из ноутбука с демонстрационными требованиями. Файлы
`invalid_submissions.jsonl` и `conflict_submissions.jsonl` подготовлены для проверок.
После пяти неверных записей в ошибочном корпусе следует корректная запись.
Учебный корпус также включён в пакет для команды `demo`.
